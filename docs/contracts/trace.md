# Trace contract: know what happened

**Goal: when a call goes wrong for anyone, the owner can see which call it was, what it tried, how far it got and where it stopped, without ever seeing what the person said. Every call carries one id that joins its row, its log lines and its response. Rows are kept for a fixed time, then deleted.**

What exists before this work, read in the code on `e061bd8`:

| Piece | State |
|---|---|
| The call log | One `call_log` row per MCP call and per web write: `function`, `started_at`, `ms`, `ok`, `error_code` (32 characters), `result_bytes`, `user_id` (`app/models.py`, `app/calllog.py`). Written in two steps, `start` then `finish`, so the write limit counts a call from its start |
| What a row never holds | An argument, a result or a crash's message. A test sends a marker in every string argument and looks for it in every column and log line (`tests/test_calllog.py`) |
| A request id | None. No row, log line or response carries one |
| Who made the call | Not on the row. A web write and an assistant's write carry the same function name |
| What a call tried | Not recorded |
| Which step failed | Only the error code. A crash's type and frames go to the log (`calllog.crash_text`), with nothing to join them to the row. A web write that loses the database is stored as `internal_error` (`app/web.py`, `logged_write`) |
| Whether anything was written | `ok` only. A duplicate and an import preview both read as ok, and neither wrote |
| Log lines | `LEVEL name: message` on stderr through one handler (`app/main.py`). Warnings always, INFO only with `AUTH_DEBUG`. The server's access line has its query string cut |
| Page loads | No row. Counted in memory for the page limit |
| Retention | None. Rows are kept for good. Deleting an account keeps its rows with no account on them (`app/services/account.py`) |
| The owner | No such thing. No setting, no column, no function and no page is for the owner alone |
| USDA failures | Every one is `usda_unavailable`, "USDA did not answer.": no answer in 5 seconds, any HTTP status, a refused redirect, a reply that is not the JSON expected, a food with no energy value (`app/services/usda.py`, `_get` returns None for all). Nothing is logged. `find_food` succeeds with `usda_note` set, so its row reads ok |
| Tool list | The same 19 functions for everyone. The library's `list_tools` can be overridden per call (`mcp/server/mcpserver/server.py`) |

## Decisions

| # | Decision | Why |
|---|---|---|
| 1 | **One id per request.** Spotter makes it, 16 hex characters from `secrets`, in a new outermost ASGI wrapper in `app/main.py`, outside the size limit, so a 413 carries one too. It is never read from the request: a caller cannot choose it. It is held in a context variable in `app/calllog.py` for the length of the request, and sent back on every response as `X-Request-Id` | One value to quote, search and join on. A caller-chosen id would be caller text in a log |
| 2 | **The id on every log line.** The `spotter` handler's format becomes `LEVEL name [id]: message`, filled by a logging filter from the context variable, `-` outside a request. The server's own access line is unchanged | The crash line and the row can be joined |
| 3 | **Seven new columns on `call_log`,** all nullable, by migration `0005`: `request_id` (indexed), `caller`, `tried`, `outcome`, `step`, `frame`, `notes`. Old rows keep nulls. Downgrade drops them | Additive, so the deploy needs one step and old code runs against the new table |
| 4 | **`caller`.** `web` or `claude`, the two names in `CALLERS` | Today nothing says which |
| 5 | **`tried`: names and counts, never a value.** A short text built from what was sent: the names of the fields sent, sorted, a space between. A list is `name[n]`. A list of objects is `name[n]{field,field}` with the fields any item sent. An object is `name{field,field}`. Only names on Spotter's own list are written: every argument name and input-model field in the tool schemas. Any other name is counted in `other[n]` and never written. One level deep: a list inside an item shows as its name only. A web write reads like the same write from an assistant: the form's fields at the top level, beside the entry's `kind` and `entry_id`. At most 400 characters: a longer one is cut at a whole name and ends ` +more`. Examples: `date entries[2]{description,kcal,meal}`; `notes sets[5]{exercise,reps,weight_kg}` | The owner sees the shape of the call. A form field's name is caller text, so only known names pass |
| 6 | **One value is written: which table.** `kind` shows its value only when it is one of Spotter's seven table names (`lift_session`, `bodyweight`, `measurement`, `food_entry`, `cardio_entry`, `saved_food`, `goal`), as `kind=food_entry`. An import also gets its rows counted by those names: `rows.kind{food_entry=80,lift_session=120}`. Any other `kind` (a goal's, a measurement's) is a name only | It says no more than the function name already does (`log_food`), and an edit or an import is unreadable without it. The owner may strike this row |
| 7 | **`outcome`: whether it did it.** One word, worked out from the result in one function both callers use: `read`, `written`, `duplicate` (the result says `duplicate: true`), `preview` (an import with `dry_run`), `refused` (a typed error), `failed` (the work itself crashed or lost the database). When the work finished and only the reply failed (step `reply`), the outcome is what the result says: a write that landed reads `written` beside `internal_error`. Null while a call runs, and for good when the process died under it | "ok" does not say whether a row was written. Today a write can commit and still answer `internal_error`, because the result is checked after the commit (`Wrapper.call`) |
| 8 | **`step`: where a failed call stopped.** One word from the error code, by one table in `app/calllog.py`: `account` (`no_subject`, `signups_closed`, `no_account`), `permission` (`not_allowed`), `limit` (`too_many_reads`, `too_many_writes`, `too_many_imported`), `lookup` (`usda_off`, `usda_unavailable`), `check` (every other code a service returns), `database` (`database_unavailable`), `crash` (`internal_error` from the work), `reply` (the result broke its schema or could not be sent). Null on success | The order a call runs in is fixed, so the code names the step |
| 9 | **`frame`: the line a crash came from.** For `crash`, `database` and `reply`: the innermost frame of the exception that lies in `app/`, as `services/food.py:306 day_numbers`. File, line and function only, never the message. A failed commit shows as `db.py` in `session_scope` | The exact place, with no edit to any service |
| 10 | **`notes`: a part that failed inside a call that went on.** Fixed words set by Spotter's own code through `calllog.note(key, word)`, stored as `key=word`, 128 characters at most. The first user is USDA (decision 12). A note set in a worker thread reaches the row | `find_food` succeeds when USDA fails. The row must still say so |
| 11 | **A web write that loses the database** is stored as `database_unavailable`, step `database`, not `internal_error`. The page shown is unchanged | The row should say what happened |
| 12 | **USDA says why.** `_get` reads the HTTP status. The reason is one of: `key_refused` (401, 403), `rate_limited` (429), `bad_request` (400), `http_NNN` (any other status), `redirect`, `no_answer` (time-out or network), `bad_reply` (not the JSON expected), `no_energy` (a food with no energy value). It goes to the row as `usda=reason` and to one warning line. Never the address, the key or the reply's text | Today a bad key, a spent hourly limit and Spotter's own bad request all read the same |
| 13 | **What the assistant is told.** The code stays `usda_unavailable` and the fix stays as it is. The message is "USDA refused Spotter's key." for `key_refused`, "USDA is over its limit for now." for `rate_limited`, and "USDA did not answer." for the rest. `find_food`'s `usda_note` and summary use the same three | The person hears "later" apart from "not working". No new code for a client to learn |
| 14 | **Retention: 90 days.** `CALL_LOG_DAYS = 90` in `app/calllog.py`. Rows older than that are deleted by one statement, on the first finished call after the process starts and then at most once in 24 hours, in the worker thread, after the call's own row is complete. A failure is logged by type and swallowed | Long enough to count active weeks over two months, short enough that the table stays small. No scheduler and nothing to set on the host |
| 15 | **The owner.** A new setting, `OWNER_USER_ID`: the sign-in provider's id of the one account that may read other people's calls, the `user_id` whoami gives and Settings shows. Unset: nobody is the owner and the read below is off. Only `app/config.py` reads it. The check is the verified token's subject against the setting, on every call | Fail closed. No id in the public repo. One setting, the owner's own to make |
| 16 | **The owner's read: `owner_calls`,** a 20th MCP function at the read level. It is in the tool list only for the owner (the server's `list_tools` leaves it out for everyone else), and a call by anyone else answers `not_allowed`, "This function is for Spotter's owner." With no person named: one line per account with a call in the window (account id, email, name, calls, failed calls, last call), and one more line, with no account on it, for the calls that had none: a refused sign-in, or a deleted account's rows. With `account_id` or `email`: that person's calls, newest first. With `no_account`: the calls that had no account. With `request_id`: that request's calls, whatever their age, and `hours` is null. Also `hours` (1 to 2,160, 24 when left out), `failed_only`, `limit` (1 to 200, 50 when left out). A call still running is not a failed call. A call row gives: `started_at` (UTC), `caller`, `function`, `ok`, `error`, `outcome`, `step`, `frame`, `tried`, `notes`, `ms`, `result_bytes`, `request_id`. Its own calls are logged like any other | The owner asks their own assistant "what happened to this person's log" and gets the rows. Everyone else's tool list is unchanged, word for word |
| 17 | **Not in a result.** No other function's result gains a field. The id reaches the caller only as the response header | Nothing another person's assistant reads changes |

## Texts added or changed

| Where | Text |
|---|---|
| `usda_unavailable`, key refused | "USDA refused Spotter's key." |
| `usda_unavailable`, over the limit | "USDA is over its limit for now." |
| `usda_note`, the same two | The message, then ": use a saved food or the person's own number." as now |
| `owner_calls` to anyone but the owner | `not_allowed`: "This function is for Spotter's owner." Fix: "Nothing to retry." |

## Work package: one builder

| Package | Files | Exit check |
|---|---|---|
| T1 | `app/calllog.py`, `app/main.py`, `app/config.py`, `app/models.py`, `app/mcp_server.py`, `app/mcp_schemas.py`, `app/web.py`, `app/services/usda.py`, `app/services/food.py`, `app/services/owner.py` (new), `app/services/__init__.py`, `migrations/versions/0005_*.py` (new), `tests/test_trace.py` (new). Existing test files only where an assertion now fails because of a decision above, each change named in the report | Every decision has a test. The id in `X-Request-Id` equals the row's `request_id` for an MCP call and for a web write, and the crash line of a crashed call carries it. The marker test covers the seven new columns, and a marker sent as a field's name (a form field, an unknown argument) reaches no column and no log line. The list of known names covers every name in the published tool schemas. Each USDA reason from a stubbed reply reaches the row, the log line and the message. A non-owner's tool list is the 19 functions byte for byte as before; the owner's has 20. Migration `0005` on SQLite: up, the models match, down. The sweep deletes a row 91 days old and keeps one 89 days old. The tests for the files touched pass, plain and with `-W error` |

Not in this work: the docs (`README.md`, `BUILD_LOG.md`), done after the review; the privacy page's "A log of calls" card, which is not served and must gain the field names, the counts and the 90 days before it is; a row for a page load; the id on an error page; which assistant app made a call (the token's client id); any eval run, since no text another person's assistant reads changes except USDA's two failure messages; setting `OWNER_USER_ID` on the host, which is the owner's.
